// TECHNICAL INTERVIEW TALKING POINTS

Architectural Deep-Dives & QA Rigor

How I answer challenging architectural questions during technical interviews for Senior & Lead SDET roles in Cybersecurity and Distributed Systems.

Q1

How do you test and measure EPP kill latency without skewing the measurement?

Traditional sleep polling introduces artificial latency. In my automation harness, I instantiate high-precision OS performance counters at the exact millisecond the child process spawns. The harness hooks into Windows Job Objects or queries process state at sub-millisecond intervals. I compute the exact delta between payload drop and process death signals, recording true kill latencies (e.g. 42.18 ms) while distinguishing parent vs. child termination order.

Q2

How do you prevent False Positives when testing Aggressive Mode against LOLBins?

Aggressive Mode is prone to killing legitimate administrative tasks if detection rules are overly broad. To prevent false positives, I engineered a dual-battery test architecture: 10 Positive Tests (containing verified threat patterns that MUST be killed) evaluated alongside 5 Negative Tests (e.g. safe PowerShell executing Get-Date, safe CMD executing dir, safe Notepad, safe Ping) that MUST NEVER be killed. A test suite only passes if positive accuracy is 100% AND negative false-positive rate is 0%.

Q3

Why build an Endpoint Performance Monitor in C# / .NET 8 rather than Python or PowerShell?

In enterprise customer environments, running third-party Python scripts requires installing runtimes, pip dependencies, or running heavy interpreted loops that consume CPU—thereby contaminating the very resource benchmark you are measuring! I architected the performance monitor as a 100% portable, single-file self-contained binary in C# .NET 8 with zero runtime prerequisites, direct Win32 kernel API bindings, and batched SQLite WAL writes. It operates with under 0.2% background overhead and zero client impact.

Q4

What does "Zero Causal Claims" mean in Performance Evidence Reports?

When customers complain about high resource utilization, QA must provide indisputable, objective engineering evidence rather than speculative opinions. My tool enforces a strict Zero Causal Claims standard: it objectively records exact normalized timestamps, PID reuses, multi-core CPU math, and host baseline context (including external applications like Chrome or backup daemons) without claiming the security agent "caused" overall system degradation. This developer-ready evidence allows developers and support to resolve Jira issues without friction.

Q5

How do you validate telemetry integrity from the endpoint to OpenSearch / SIEM?

In our E2E BlackBox suite, testing doesn't stop at endpoint process termination. The test harness queries the OpenSearch / Elasticsearch REST API using dynamic tenant indices to verify that the generated telemetry event was properly normalized, enriched with MITRE ATT&CK technique IDs (e.g. T1036.001), and matched the exact source host name and risk score.

Q6

How do you debug container microservices issues in a live security stack?

During a live system health audit of distributed container clusters, I inspected microservice container logs and identified a fatal startup crash in an active containment daemon. By analyzing the Python traceback, I found an import collision between legacy websocket libraries. I fixed the container virtualenv build, and resolved an OpenSearch type mapping mismatch (long vs float on disk metrics) that had been silently dropping telemetry documents.
